# Charaideo Reserve — Headless Shopify Storefront

## Compressed, Context-Aware Product and Architecture Specification

Build a production-ready headless Shopify storefront for **Charaideo Reserve**, an Assam-origin tea brand, using the current Shopify Hydrogen architecture, React Router conventions, TypeScript, GraphQL, Shopify Storefront API, Customer Account API, Admin GraphQL API, Shopify Checkout, and Oxygen.

The application must support:

1. Standard Shopify product purchases.
2. A configurable custom tea box builder.
3. Ingredient-level gram inventory.
4. Secure server-side pricing and validation.
5. Shopify-native merchant configuration.
6. Customer accounts, saved boxes, wishlist, and order history.
7. Oxygen deployment and real Shopify connectivity in local development.

This is a production commerce system, not a front-end mockup.

---

## 1. Core Architecture

Use the current Hydrogen project structure generated by Shopify.

Do not build a generic Vite SPA.

Do not add a fake `index.html` to bypass Hydrogen build errors.

The application must use the official Hydrogen build pipeline, including the current:

- Hydrogen/Vite configuration
- React Router server entry
- Oxygen adapter
- package scripts
- environment conventions
- deployment commands

Required runtime model:

```text
Browser
   ↓
Hydrogen / Oxygen
   ├── Storefront API
   ├── Customer Account API
   ├── secure server-side Admin GraphQL API
   └── Shopify Checkout
```

Shopify is the commerce source of truth.

Hydrogen owns presentation, customer interaction, custom-box orchestration, and server-side domain validation.

## 2. API Boundaries

### Storefront API

Use for customer-facing:

- Products and variants
- Collections
- Search
- Prices
- Availability
- Storefront-visible metafields
- Cart and cart lines
- Discounts where supported
- Checkout URL
- Storefront content

Do not use Admin API for ordinary catalog rendering.

### Customer Account API

Use for:

- Login and logout
- Customer profile
- Addresses
- Orders and order history
- Account information
- Customer-authenticated saved-box experiences where supported

Do not implement custom password authentication.

### Admin GraphQL API

Use only in secure server-side code for:

- Product creation and updates
- Metafields and metaobjects
- Inventory operations
- Order processing
- Webhook-related actions
- Custom tea inventory adjustments
- Merchant operations unavailable through Storefront API

Never expose an Admin token to browser code.

```text

```

Examples:

```text

```

Use integer grams internally. Never use floating-point kilograms for inventory calculations.

## 8. Custom Tea Box Concept

The box is one outer package containing separately packed tea packets.

```text
ONE OUTER BOX
   ├── Hapjan Black — 10g
   ├── Makolbari Black — 15g
   └── Guwahati Green — 5g
```

Use customer-facing language such as:

- Create Your Tea Box
- Build Your Tea Selection
- Create Your Collection

Do not imply that all teas are physically mixed unless that is actually the fulfillment process.

`CustomBlend` may remain an internal technical name.

---

## 9. Custom Box Rules

The following rules are mandatory and configurable where stated.

### Unique products

Maximum unique teas defaults to 10.

### Same category

Different products in the same category are valid:

```text
Hapjan Black — 10g
Makolbari Black — 15g
```

### Single tea

One tea is valid:

```text
Hapjan Black — 100g
```

### Weight increment

Every item must use the global increment. Current increment: 5g.

Valid:

```text
5, 10, 15, 20, 25
```

Invalid:

```text
6, 12, 17, 23
```

### Total weight

Total grams must be between configured minimum and maximum.

### Per-product limits

Each product may define its own minimum and maximum contribution.

Example:

```text
Rare Oolong: maximum 25g
Hapjan Black: maximum 100g
```

### Eligibility

Only products marked blend-eligible may be selected.

## 10. Pricing

Calculate custom-box pricing from current ingredient configuration.

Example:

```text
Hapjan Black: ₹2/g × 10g = ₹20
Makolbari Black: ₹3/g × 15g = ₹45
Guwahati Green: ₹2.50/g × 5g = ₹12.50

Tea subtotal = ₹77.50
```

Apply configured packaging logic internally.

Customer-facing display may show one simple total.

Never trust client-supplied prices. The client may submit product IDs, variant IDs, and grams, but the server must reload current Shopify data and calculate the authoritative price.

Centralize currency calculations and rounding. Do not use unsafe floating-point arithmetic.

## 15. Inventory Lifecycle

Inventory is tracked per individual tea product.

Example:

```text
Hapjan Black: 25,000g
Makolbari Black: 15,000g
Guwahati Green: 50,000g
```

Order:

```text
Hapjan Black: 10g
Makolbari Black: 15g
Guwahati Green: 5g
```

Result:

```text
Hapjan Black: 24,990g
Makolbari Black: 14,985g
Guwahati Green: 49,995g
```

Do not permanently deduct inventory when the customer:

- Opens the builder
- Selects a tea
- Saves a box
- Adds a box to cart
- Opens checkout
- Abandons checkout

The required deduction event is successful Shopify order creation.

## 16. Order Webhook and Inventory Processing

Implement a verified Shopify order-created webhook.

Workflow:

```text
Shopify order created
        ↓
Verify webhook
        ↓
Detect custom tea box
        ↓
Parse structured components
        ↓
Validate component IDs and grams
        ↓
Adjust each tea inventory by grams
        ↓
Record successful processing
```

Webhook processing must be idempotent.

Use a durable idempotency key based on order ID plus event/action identity.

If the same webhook is delivered twice:

```text
First delivery: adjust inventory
Second delivery: return success without adjusting again
```

Never allow a retry to deduct twice.

Log:

- Validation failures
- Admin API failures
- Inventory adjustments
- Duplicate webhook deliveries
- Missing component data
- Oversell conditions

Never log tokens or sensitive customer data.

## 17. Inventory Concurrency and Restocking

Handle stale inventory and concurrent orders.

Example:

```text
20g Oolong remains.
Customer A requests 15g.
Customer B requests 15g.
```

At minimum:

- Revalidate at Add to Cart
- Revalidate before relevant cart mutations
- Rely on Shopify checkout availability where supported
- Validate inventory during order processing
- Log exceptional oversell conditions

Use the strongest current Shopify reservation/component strategy practical for the implementation.

For cancellation and restocking:

- Distinguish cancellation, refund, restock, and fulfillment
- Do not restore inventory for every refund automatically
- Prefer Shopify’s authoritative restock state
- Make restoration idempotent

## 36. Non-Negotiable Principles

- Shopify is the commerce and merchant source of truth.
- Hydrogen is the customer-facing application.
- Oxygen is the production runtime.
- Storefront API is for storefront commerce.
- Customer Account API is for buyer-authenticated experiences.
- Admin GraphQL is for privileged server-side operations.
- One loose-tea inventory unit equals one gram.
- Inventory is tracked per individual tea product, never by category.
- Custom-box rules come from merchant configuration.
- Prices are recalculated and validated server-side.
- Inventory is not deducted on cart creation.
- Inventory is adjusted after successful order creation.
- Webhook processing is verified and idempotent.
- Shopify Checkout handles payment and checkout.
- Fulfillment must receive the complete packet breakdown.
- The design system must be token-driven and rebrandable.
- Do not compromise Hydrogen architecture merely to make a generic Vite build pass.
- Build a real production commerce application, not a visual prototype.
